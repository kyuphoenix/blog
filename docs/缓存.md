## 1. 为什么需要分层缓存？

在基于 Serverless / Edge Function 与 GitHub 内容解耦的博客系统中，常常面临两个核心矛盾：
1. **GitHub API 频率限制（Rate Limit）**：未授权访问每小时仅 60 次，即使带 Token 也仅 5000 次/小时。若无强缓存，多读者并发或频繁冷启动会瞬间击穿限额。
2. **边缘冷启动与延迟**：Serverless 容器在无请求数分钟后会被平台冻结销毁，新访客访问时需要重新执行函数与动态抓取。

本项目通过**四层渐进式分层缓存 + SWR** 完美解决了这一难题：**让 99% 的读者请求直接由全球 300+ 城市的边缘 CDN 节点在 20ms 内直接返回编译好的静态 HTML，只有在博主真正提交新文章时才向 GitHub 发起 1 次请求**。

## 2. 四层渐进式缓存架构

```
                  访客访问
                     │
                     ▼
┌────────────────────────────────────────────────────────┐
│ 第一层：客户端浏览器 (Browser)                             │ ── max-age=0, must-revalidate (确保更新即时可见)
└────────────────────────────────────────────────────────┘
                     │
                     ▼
┌────────────────────────────────────────────────────────┐
│ 第二层：全球边缘 CDN (Cloudflare / Netlify / Vercel)      │ ── s-maxage=86400 (24h强缓存), stale-while-revalidate=604800 (7d)
└────────────────────────────────────────────────────────┘
                     │ CDN未命中/后台SWR静默预取
                     ▼
┌────────────────────────────────────────────────────────┐
│ 第三层：服务层持久化存储 (Cloudflare KV / Unstorage)      │ ── CACHE_TTL=86400 (24h常驻，无需每次调GitHub)
└────────────────────────────────────────────────────────┘
                     │ KV过期或主动Purge强制清空
                     ▼
┌────────────────────────────────────────────────────────┐
│ 第四层：GitHub Raw / REST API 源数据                     │ ── 仅在内容变更且Purge后请求 1 次
└────────────────────────────────────────────────────────┘
```

### 各层职责分工：

| 层级 | 缓存位置 | 缓存策略 | 作用与体验 |
| :--- | :--- | :--- | :--- |
| **第一层：浏览器端** | 读者本地设备 | `max-age=0, must-revalidate` | 读者刷新或导航时，浏览器总是向最近的边缘 CDN 确认最新状态。一旦博主更新文章并清空 CDN，**读者立刻看到最新内容，绝不会被本地磁盘死缓存卡住**。 |
| **第二层：边缘 CDN** | 全球 300+ 机房 | `s-maxage=86400` + `stale-while-revalidate=604800` | **24 小时强缓存**：所有正常读者秒级命中静态 HTML，0 毫秒函数冷启动，0 次请求 GitHub。<br>**7 天 SWR 平滑过渡**：超过 24 小时后，边缘 CDN 依然微秒级返回陈旧副本，同时后台异步静默从源站预取最新版本，读者体验永远零等待。 |
| **第三层：数据存储层**| Worker KV / 内存 | `CACHE_TTL=86400`（24小时） | 底层清单与文章数据常驻边缘 KV。就算 CDN 节点偶发失效穿透，后端函数也直接从本地 KV 读数据，依然不打扰 GitHub。 |
| **第四层：源数据源** | GitHub 仓库 | 源头 Markdown / JSON | 仅在初次构建或触发主动 Purge 时请求 1 次。 |

## 3. 三大云平台边缘控制头适配

代码在 [`src/utils/cache.ts`](../src/utils/cache.ts) 中对全站页面路由及 API 接口统一注入了针对三大云平台的专用指令：

* **Cloudflare (Workers / Pages)**：
  - 注入高优先级的 `Cloudflare-CDN-Cache-Control` 与 `CDN-Cache-Control`：
    ```http
    Cloudflare-CDN-Cache-Control: public, max-age=86400, stale-while-revalidate=604800
    CDN-Cache-Control: public, max-age=86400, stale-while-revalidate=604800
    ```
* **Netlify (Edge Functions)**：
  - 注入专用指令与细粒度标签（Cache Tag）：
    ```http
    Netlify-CDN-Cache-Control: public, max-age=86400, stale-while-revalidate=604800
    Netlify-Cache-Tag: page,post,post-文章名,all-posts
    ```
* **Vercel (Edge Runtime)**：
  - 注入标准共享缓存头与标签：
    ```http
    Cache-Control: public, max-age=0, s-maxage=86400, stale-while-revalidate=604800, must-revalidate
    Vercel-Cache-Tag: page,post,post-文章名,all-posts
    ```
* **404 与敏感操作接口**：
  - 动态接口、管理端点及 404 文章不存在页面自动设置 `no-cache, no-store`，严防错误状态被意外缓存。

## 4. 强制缓存失效工作流 (Cache Purge)

当博主新增、修改或删除了文章时，如何确保全球所有机房的 CDN 缓存同步刷新？

### 4.1 自动刷新 (发布/修改文章)
当你在本地推送 Git 提交，或在 **Pages CMS** 后台修改保存文章（`posts/**`）、修改站点设置（`blog.config.json`）、编辑友链（`friends.json`）或修改关于页（`about.md`）时：
1. 自动触发 GitHub Actions 工作流 [`.github/workflows/sync-posts.yml`](../.github/workflows/sync-posts.yml)；
2. 自动更新生成 `posts/manifest.json`；
3. **通知博客后端**：调用 `${BLOG_URL}/api/posts/purge` 清空底层数据并重新预热；
4. **广播全球 CDN 强制清除**：根据你配置的凭证，自动调用 Cloudflare / Netlify / Vercel 官方控制平面接口，毫秒级清空对应平台的边缘缓存。

### 4.2 手动一键全局强刷
在不改动任何代码的情况下，你可以随时手动清除全网所有机房缓存：
1. 进入 GitHub 仓库页面 -> 点击 **Actions** 标签页；
2. 在左侧工作流列表中选择 **Force Purge All Caches**；
3. 点击右侧 **Run workflow** 按钮，支持勾选指定平台，点击运行即可一键全量清空！

### 4.3 Pages CMS 后台动作联动
在 Pages CMS 后台的「站点设置」或「友情链接」页面中，预置了 **「刷新缓存」** 动作按钮，点击后将直接通知工作流执行全链路同步与刷新。

## 5. 环境变量与凭证配置指南

### 5.1 配置总览表格

配置路径：GitHub 仓库 -> **Settings** -> **Secrets and variables** -> **Actions**

| 变量名称 | 所属平台 | 建议存放位置 | 必填/可选 | 说明与获取方式 |
| :--- | :---: | :---: | :---: | :--- |
| **`BLOG_URL`** | **通用** | Variables 或 Secrets | **必填** | 博客在线访问地址 (如 `https://blog.example.com`)，用于通知后端清空 KV/数据缓存 |
| **`PURGE_SECRET`** | **通用** | Secrets | **推荐** | 缓存刷新鉴权密钥 (需与后端一致，未配置时自动兼容 `GH_TOKEN` / `GITHUB_TOKEN`) |
| **`CLOUDFLARE_ZONE_ID`** | **Cloudflare** | Secrets 或 Variables | 可选 | 域名 Zone ID (在 Cloudflare 域名控制台概述页面右侧直接复制) |
| **`CLOUDFLARE_API_TOKEN`** | **Cloudflare** | Secrets | 部署必填 / 强刷复用 | **部署时使用的 `CLOUDFLARE_API_TOKEN` 直接复用**（创建时**必须追加** `Zone - Cache Purge - Purge` 权限） |
| **`NETLIFY_SITE_ID`** | **Netlify** | Secrets 或 Variables | 可选 | 目标项目 ID（Netlify 对应项目 -> **Project configuration** -> 复制顶部的 **Project ID**） |
| **`NETLIFY_API_KEY`** | **Netlify** | Secrets | 部署必填 / 强刷复用 | **部署时创建的 PAT 密钥直接复用**（变量名 `NETLIFY_API_KEY` 或 `NETLIFY_AUTH_TOKEN`） |
| **`VERCEL_TOKEN`** | **Vercel** | Secrets | 部署必填 / 强刷复用 | **部署时配置过的 `VERCEL_TOKEN` 直接复用**，通过官方 Edge Cache REST API 刷新 |
| **`VERCEL_PROJECT_ID`** | **Vercel** | Secrets 或 Variables | 可选 | **部署时配置过的 `VERCEL_PROJECT_ID` 直接复用**，无需在 Vercel 绑定 Git 仓库 |
| **`VERCEL_ORG_ID`** | **Vercel** | Secrets 或 Variables | 可选 | 若项目部署在 Vercel 团队下填写 Team ID（个人账号留空即可） |
| **`CACHE_TTL`** | **通用** | Variables | 可选 | 底层存储/KV 默认缓存秒数 (默认 `86400` 即 24 小时) |

### 5.2 平台凭证获取与权限精简指南

#### ⚡ 1. Cloudflare：一币两用，创建 Token 时必须追加 Cache Purge 权限
在部署 Cloudflare Worker 时，本来就需要创建 `CLOUDFLARE_API_TOKEN`：
* 在 Cloudflare 控制台创建 Token 时，基于 **Edit Cloudflare Workers** 模板；
* 在权限列表（Permissions）中**必须点击 Add more 追加一项**：
  * **`Zone`** -> **`Cache Purge`** -> **`Purge`**
* 在 Zone Resources 区域选择 `Include` -> `All zones`（或选定你博客绑定的域名）；
* ⚠️ **必须追加的原因**：发布文章时自动刷新或手动一键强刷 CDN 时，GitHub Actions 将直接调用 Cloudflare 官方 Cache Purge API。**若未在此 Token 中添加 Purge 权限，强刷操作将失败并返回 403 Forbidden**。在创建时一次性追加后，同一枚 Token 即可完美支持 Worker 自动化构建部署与全网 300+ 机房的 CDN 缓存毫秒级强刷！

#### 🌐 2. Netlify：无缝复用部署用 PAT
* **`NETLIFY_SITE_ID`**：在 Netlify 对应项目页面，点击左侧菜单 **Project configuration**，在顶部直接复制 **Project ID**。
* **`NETLIFY_API_KEY`**：若之前已配置部署工作流，直接使用当时的 Personal Access Token 即可，两边变量名称完全通用。

#### ▲ 3. Vercel：官方 REST API，彻底解除 GitHub 仓库绑定限制
* 传统的 Vercel Deploy Hook 强制要求在 Vercel 控制台连接 GitHub 仓库，但通过 GitHub Actions CLI 部署的项目在 Vercel 看来是外部上传的，无法创建 Deploy Hook。
* 本项目改用 **Vercel 官方 Edge Cache Invalidation REST API**：
  直接复用部署必须的 **`VERCEL_TOKEN`** 与 **`VERCEL_PROJECT_ID`**，自动按标签标记失效，**无需绑定任何 Git 仓库，无需创建 Deploy Hook**！

### 5.3 部署解耦说明 (无配置零阻断)

1. **部署阶段 100% 独立**：
   部署工作流（`deploy.yml`、`deploy-vercel.yml`、`deploy-netlify.yml`）只关注编译代码与发布，完全不依赖任何 Cache Purge 变量。
2. **清理工作流安全兜底**：
   在 `sync-posts.yml` 与 `purge-cache.yml` 中，针对每个平台的清理都有判空守卫。若你尚未填写某个平台的 ID，Actions **仅会输出一行提示并优雅跳过，状态依然为绿色的成功（Success）**，绝不阻塞流程。
3. **随手补填即可激活**：
   你完全可以先完成博客项目的首次部署，待各平台部署成功分配好 Project ID / Zone ID 后，随时在 GitHub Secrets 中补填，即可无缝激活全网 CDN 强刷能力！
